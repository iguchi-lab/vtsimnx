# 空調の潜熱処理と湿度境界

室内湿度を見て運転する新しい制御は[室温・室湿度の制御モード](aircon_room_humidity_modes.md)を参照。
本書の `pre_rh` の説明は、既定の `control_mode="temperature_priority"` に対応する。

> **使い方** — 先に [入力JSONの組み立て](ai_input_guide.md) と [空調のモデルと制御](aircon_model_and_control.md)。正本は [moisture_network_phase1.md](../engine/docs/moisture_network_phase1.md)。

冷房時の除湿と、空調ノードの吹出湿度の扱いです。温度優先の `pre_rh`（設定相対湿度 %）は室RH未達の評価用です。冷却と独立した除湿や吹出湿度の指定は行いません。

現行パッケージは v1.8.1 です。本文は2026-11-14の温度優先・付随除湿の修正を反映しています。潜熱の各方式は空調章、湿気の行列は実装契約を参照してください。

## 1. 室の湿度と空調の吹出湿度

室の `calc_x=true` は、絶対湿度を湿気収支の未知数として解く指定である。
空調はbuilder/parser上では `calc_x=false` だが、ソルバ内の役割は運転状態で切り替える。
実際に除湿している冷房は吹出絶対湿度を固定境界とし、暖房・停止・除湿量ゼロの冷房は
湿気回路網の混合未知数として同時に解く。`AUTO` の暖房側も混合未知数である。
`set` 側の `calc_c` は従来どおり空調ノードへ引き継ぐが、`calc_x` は引き継がない。

未知数・固定境界の区別は `humiditySolveNode` に共通化し、求解・緩和・前時刻への復元・
物理範囲検査で同じ判定を用いる。吸込湿度の古い値を吹出へコピーして固定する処理は行わない。
非連成の湿気求解では未知数だけを前時刻へ戻し、外気や除湿中の吹出固定境界は保持する。

## 2. 空調接続枝の扱い

空調ノードに直接接続する換気枝は、吸込側・吹出側とも湿気移流に含める。
換気・熱計算の風量と、湿気の搬送を切り離さない。除湿中は吹出 `current_x`
を固定境界とする。暖房・停止・除湿不要の冷房では、流入と流出の水分収支を同時に解く。

同一室内の循環では吸込と吹出の水分移動が打ち消し合う。`in` と `out` が異なる室
（全館空調のホール還気→各室吹出など）でも、風量に乗った室間の湿気混合は残る。
循環による架空の除湿を防ぐため、除湿量ゼロの空調を固定湿度境界にしない。

同一の上流・下流ノード間に複数枝がある場合、湿気の質量流量は合算する。
濃度計算でも枝ごとの除去率を掛けた有効流量を合算する。

## 3. `pre_rh` の入力と計算

`aircon[].pre_rh`、または空調ノードの `pre_rh` に相対湿度[%]を指定する。
値域は `0 < pre_rh <= 100` で、定数または計算時刻数に対応する配列を与える。
温度優先では `pre_rh` の有無によらず `ac_spec.latent_method` を用いる。スケジュール配列は
[`schedule_usage.md`](schedule_usage.md)を参照する。

次は既存モデルへ追加する空調設定の抜粋である。参照する室・外気ノード、湿気計算の有効化、
初期温湿度、容量、境界条件は別途モデル側で指定する。風量はm³/sで与える。

```json
{
  "aircon": [{
    "key": "AC1",
    "in": "室1",
    "out": "室1",
    "set": "室1",
    "outside": "外気",
    "vol": 0.1,
    "pre_temp": 26.0,
    "pre_rh": 50.0,
    "mode": "COOLING",
    "model": "RAC"
  }]
}
```

温度優先では室温要求から冷却運転・吹出温度を決め、吸込状態と `latent_method` から
冷却に伴う除湿量を求める。`pre_rh` は実際の設定対象室RHの上限超過を評価するためだけに使う。

$$
x_{\mathrm{supply}}=\min(x_{\mathrm{in}},x_{\mathrm{latent\ method}},x_{\mathrm{sat}}(T_{\mathrm{supply}})).
$$

例えば `pre_temp=27`、`pre_rh=60` でも、27℃・60％の重量絶対湿度へ吹出を強制しない。
小さな冷却でコイルが乾いていれば除湿量は0となり、室RHが60％を超えても温度要求だけで運転する。
実装ではfloat32出力の丸めによる100％超過を防ぐため、飽和絶対湿度に約0.95 ppmの余裕を設ける。
空調直後の出口節点が、容量・発熱・発湿・他系統からの流入を持たない純粋な分岐点の場合は、
その水分収支 `q_out * x_out = q_in * x_supply` も上限に反映する。
風量計算の微小な残差で出口湿度が増幅される場合は、
`x_supply <= x_sat(T_out) * q_out / q_in` となるよう空調側で追加除湿し、湿気回路網を解き直す。
出口の結果値を切り詰める処理は行わない。並列枝・逆向き流れも実際の流向で合算し、
容量や混合・熱源・水分源を持つ一般の室にはこの分岐点の式を適用しない。
分岐点の最終受理では、倍精度の計算値とfloat32で保存する温湿度の両方でRHが100％以下であることを確認する。
上記の余裕を含む境界目標と物理的な飽和上限は区別する。線形求解の丸めによって目標を微小に超えても、
水分収支と両方の飽和検査を満たす状態は受理する。100％を超える状態を許容する誤差幅は設けない。
凝縮水量は `rho0 * abs(vol) * (x_in - x_supply)` [kg/s]、
潜熱処理量はこの凝縮水量と吹出温度の蒸発潜熱から求める。
湿りエンタルピー連成では最終吹出状態から全熱・顕潜熱を再評価する。

`pre_rh` は `latent_method` を上書きしない。加湿はせず、吹出の飽和制約は常に適用する。
室湿度は発湿・換気・蓄積を含む収支で決まり、室RHを設定値へ直接固定する指定ではない。
湿度超過だけで機器を起動しないため、温度制御でOFFになった期間の単独除湿は行わない。

冷却に伴う潜熱処理も**後段の全熱能力判定の対象となる**。
最大能力を超えれば実効設定温度の探索・再計算を行う。飽和制約のための追加潜熱も
能力・消費電力の計算に含め、除湿量を削って過飽和のまま受理しない。

## 4. 潜熱処理の選択と再計算

温度優先では、95%法、バイパスファクター法、コイル面積法、潜熱処理なしの
いずれかを用いる。各方式の式と制約は[第10章の10.4節](aircon_model_and_control.md)にまとめた。
全方式で顕熱計算後の吹出温度による飽和制約を共用する。`none` でも過飽和を防ぐための凝縮は行う。
潜熱処理と吹出湿度の適用は能力判定の内部で行う。全機の吹出湿度境界が安定するまでは能力探索を進めない。全館空調の風量判定では負荷を再評価するが、吹出湿度を重複更新しない。
再計算理由の優先順位が「運転・停止、能力、風量、吹出湿度」であることと、潜熱計算を最後に
行うことは同義ではない。

| 判定・設定 | 現行の扱い |
|---|---|
| 吹出絶対湿度の外側再計算 | 緩和前の目標との差が min(連成湿度許容値, 1e-7 kg/kg) を超えたとき、飽和超過時、または役割変更時 |
| 除湿中の境界更新 | 緩和率は既定0.5。同じ制御候補の残差履歴から0.1～1.0の割線加速を適用（湿度優先は直接更新）。飽和上限を即時適用し再求解。許容内なら変更しない |
| 潜熱フィードバック緩和 | `simulation.coupling.latent_relaxation` の既定値は0.5 |

旧来の `1e-4` の判定床は使わない。湿度の線形ソルバ残差許容値とは単位も意味も異なる。
最終受理時には同じ吹出湿度・飽和基準を確認し、採用する湿度の水分収支を再評価し、連成湿度の絶対許容値に加え、
線形ソルバと同じ行スケーリング・右辺ノルムによる相対残差基準を満たすことを要求する。
共通の成功判定は[計算ループ](../engine/docs/simulation_loops.md)を参照する。
温度による運転・停止と最低能力の扱いは[全館空調の風量制御](duct_central_airflow_control.md)を参照する。
