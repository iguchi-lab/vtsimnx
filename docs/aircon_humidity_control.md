# 空調の潜熱処理と湿度境界

> **使い方** — 先に [入力JSONの組み立て](ai_input_guide.md) と [空調のモデルと制御](aircon_model_and_control.md)。正本は [moisture_network_phase1.md](../engine/docs/moisture_network_phase1.md)。

冷房時の除湿と、空調ノードの吹出湿度の扱いです。`pre_rh`（設定相対湿度 %）は、室の相対湿度をその値に固定する指定ではありません。吹出の絶対湿度と除湿量を決める分岐です。

現行パッケージは v1.8.1 です。本文の対象実装は改訂時点の v1.8.0 / commit `ef11982` です。潜熱の各方式は空調章、湿気の行列は技術文書 7.3 節を参照してください。

## 1. 室の湿度と空調の吹出湿度

室の `calc_x=true` は、絶対湿度を湿気収支の未知数として解く指定である。
一方、`type="aircon"` のノードは **吹出絶対湿度を与える固定境界**であり、
builderは `calc_x=false` とする。solverへ直接 `calc_x=true` を渡してもparserでfalseへ変更される。
空調ノードの `current_x` は空調計算で更新されるため、固定境界は「全時刻で同じ値」を意味しない。
`set` 側の `calc_c` は従来どおり空調ノードへ引き継ぐが、`calc_x` は引き継がない。

各外側反復の物理求解前に、停止中・非冷房、または `current_x` が非有限値もしくは
`1e-4 kg/kg(DA)` 以下の空調ノードを、`in_node` の絶対湿度に同期する。
非連成の湿気求解で前時刻値へ戻す対象は湿気未知ノードのみであり、
外気や空調吹出などの固定境界は外側反復で更新した値を保持する。

## 2. 空調接続枝の扱い

空調ノードに直接接続する換気枝は、吸込側・吹出側とも湿気移流に含める。
換気・熱計算の風量と、湿気の搬送を切り離さない。冷房 ON では吹出 `current_x`
（`supplyX`）を固定境界として除湿を反映する。暖房・停止では求解前に吸込絶対湿度へ
同期し、除湿せずに還気の湿気をそのまま吹出へ渡す。

同一室内の循環では吸込と吹出の水分移動が打ち消し合う。`in` と `out` が異なる室
（全館空調のホール還気→各室吹出など）でも、風量に乗った室間の湿気混合は残る。
古い低湿度 `supplyX` による過乾燥は、枝を切るのではなく吸込同期で防ぐ。

同一の上流・下流ノード間に複数枝がある場合、湿気の質量流量は合算する。
濃度計算でも枝ごとの除去率を掛けた有効流量を合算する。

## 3. `pre_rh` の入力と計算

`aircon[].pre_rh`、または空調ノードの `pre_rh` に相対湿度[%]を指定する。
値域は `0 < pre_rh <= 100` で、定数または計算時刻数に対応する配列を与える。
適用条件に該当しなければ `ac_spec.latent_method` を用いる。スケジュール配列は
[`schedule_usage.md`](schedule_usage.md)を参照する。

次は既存モデルへ追加する空調設定の抜粋である。参照する室・外気ノード、湿気計算の有効化、
初期温湿度、容量、境界条件は別途モデル側で指定する。風量はm³/sで与える。

```json
{
  "aircon": [{
    "key": "AC1",
    "in": "室1",
    "out": "室1",
    "set": "室1",
    "outside": "外気",
    "vol": 0.1,
    "pre_temp": 26.0,
    "pre_rh": 50.0,
    "mode": "COOLING",
    "model": "RAC"
  }]
}
```

空調が冷房運転中で正の処理風量を持つとき、吸込温度 `T_in` と設定相対湿度から目標を求める。

$$
x_{\mathrm{sp}}=x(T_{\mathrm{in}},\phi_{\mathrm{req}}),\quad
\phi_{\mathrm{req}}=\mathrm{pre\_rh}/100,\qquad
x_{\mathrm{in}}>x_{\mathrm{sp}}\ \Rightarrow\ x_{\mathrm{supply}}=x_{\mathrm{sp}}.
$$

上式の相対湿度は比率で表す。実装の `absolute_humidity` 関数へは百分率のまま渡す。

ここで `T_in` と `x_in` は **`in_node` の状態**であり、遠隔の `set_node` や
`pre_temp` の値から目標を求めるわけではない。凝縮水量は
`rho0 * abs(vol) * (x_in - x_supply)` [kg/s]となる。
室の相対湿度を設定値へ直接拘束する機能ではなく、室湿度は発湿・換気・蓄積を含む収支で決まる。
湿度超過だけでは空調を起動しないため、温度制御でOFFになった期間の単独除湿は行わない。

目標超過時は `latent_method` より優先する。`latent_method="none"` でも
`pre_rh` による除湿は有効である。目標以下では `latent_method` に戻るため、
`pre_rh` は除湿を停止する下限でもなく、従来のコイルモデルでさらに除湿する場合がある。

この分岐の吹出湿度はコイルの能力・機種特性によらず決まるが、**後段の全熱能力判定は残る**。
最大能力を超えれば実効設定温度の探索・再計算が行われ、条件によっては収束できない。
さらに、この分岐には吹出温度での飽和湿度による制限がないため、低い吹出温度では
過飽和となる可能性がある。実機のコイル状態や消費電力の再現を保証する機能ではない。

## 4. 潜熱処理の選択と再計算

理想除湿が適用されない場合は、95%法、バイパスファクター法、コイル面積法、潜熱処理なしの
いずれかを用いる。各方式の式と制約は[第10章の10.4節](aircon_model_and_control.md)にまとめた。
潜熱処理と吹出湿度の適用は能力判定の内部で先に行われ、全館空調の風量判定でも再評価する。
再計算理由の優先順位が「運転・停止、能力、風量、吹出湿度」であることと、潜熱計算を最後に
行うことは同義ではない。

| 判定・設定 | v1.7.5の扱い |
|---|---|
| 吹出絶対湿度の外側再計算 | 変化量が `max(coupling_humidity許容値, 1e-4)` kg/kg(DA)を超えたとき |
| 潜熱フィードバック緩和 | `simulation.coupling.latent_relaxation` の既定値は0.5 |

吹出 `current_x` は閾値以下の変化でも更新するが、その更新だけでは同一時刻の再求解を要求しない。
閾値は解の精度保証ではなく反復を制御する数値設定である。湿度の線形ソルバ残差許容値とは区別する。
温度による運転・停止と最低能力の扱いは[全館空調の風量制御](duct_central_airflow_control.md)を参照する。
