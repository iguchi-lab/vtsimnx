# 室温・室湿度の制御モード

`aircon[].control_mode` は温湿度の制御目的を指定する。省略時は
`temperature_priority` で、室温要求に従って運転する。`mode`（暖房・冷房・停止）、
`model`（COPモデル）、`ac_spec.latent_method`（従来の潜熱処理方式）とは別の指定である。

| control_mode | 冷房時の動作 |
|---|---|
| `temperature_priority` | 室温要求で運転し、`latent_method` に従って冷却に伴う除湿だけを行う。`pre_rh` は室RHの未達評価に使い、吹出湿度の強制指定や湿度単独の運転はしない。 |
| `humidity_priority` | 室湿度の要求でも運転する。指定した `latent_method` による冷却除湿を行い、室温を設定温度から `max_overcooling` K まで下げられる。再熱は行わない。 |
| `temperature_humidity` | 室温設定と室RH上限の両立を目指す。理想コイルで除湿し、必要に応じて再熱する。冷却コイル能力が不足する場合は温度を優先し、残る湿度超過を出力する。 |

新しい2モードの `pre_rh=60` は、**設定対象室のRHを60％以下にする除湿要求**を意味する。
乾燥時には加湿しない。湿度優先のRHは実際の室温で評価する。
温湿度満足の必要水分量は要求設定温度で評価し、出力するRH未達は実際の室温による。

```json
{
  "key": "AC",
  "set": "LD",
  "in": "return",
  "out": "supply",
  "outside": "outside",
  "mode": "COOLING",
  "model": "RAC",
  "pre_temp": 26.0,
  "pre_rh": 60.0,
  "control_mode": "temperature_humidity",
  "max_overcooling": 2.0,
  "min_coil_temperature": 5.0,
  "reheat_cop": 1.0,
  "vol": 0.1
}
```

これは既存入力の空調部分の抜粋。別途 `ac_spec`、参照ノード、換気・熱回路を指定する。
`calc_flag.x=true`、設定対象室の `calc_x=true` / `calc_t=true` が必要。
新モードでは `COOLING` / `HEATING` / `OFF` を明示し、`AUTO` は使用しない。
暖房時は従来の温度制御、停止時は除湿を行わない。各時刻の設定温度・湿度を使用する。

湿度優先で、その送風量では過冷却下限を保つためにコイルの加熱が必要になる場合は、その風量候補の冷房・除湿を停止する。同じ候補の反復では停止によって還気が変わっても再起動を繰り返さない。DUCT_CENTRALでは別の風量候補も計算し、成立する候補を選ぶ。湿度未達量はそのまま出力し、再熱や温度の書き換えで達成したことにはしない。

乾いた還気の送風だけで目標湿度を満たす場合もあるため、湿度優先ではまず加熱せずに維持できる最も高い室温を求め、その状態でも除湿が必要な場合にコイルを冷やす。乾いた空気の温度だけを下げるとRHが上がるため、この順序を逆にしない。湿度要求を受けて始めた送風は、その送風によって要求が解消しただけでは同じ時間ステップ内に停止させない。送風のみの場合は顕熱・潜熱・再熱負荷を発生させず、DUCT_CENTRALの送風電力を計上する。次の時間ステップでは要求を改めて判定する。

## 理想設備としての前提

制御モードは機種固有の除湿運転を再現するものではなく、選択したコイルモデルと機器能力による比較用の制御である。
`humidity_priority` は `ideal_coil`（省略時）、`none` / `rh100`（理想飽和コイルの別名）、`rh95`、`bf`、`coil_aoaf` を使用できる。選択した方式の吹出絶対湿度を逆算し、過冷却幅・コイル面温度・能力の制約内で室湿度を合わせる。BF法とコイル面積法では吹出温度とコイル面温度を区別して下限を適用する。

`temperature_humidity` は `ideal_coil`（省略時、`none` / `rh100` も同義）と再熱を使用する。その他の潜熱方式との組合せは入力エラーになる。指定された `max_overcooling` は使用しないため、builder が警告する。
吸込・吹出・設定対象室は別室にできる。除湿目標は湿気回路網を用いて、発湿、外気流入、
水分蓄積、材料との水分交換を含めて算定する。室湿度の結果値を直接固定・切り詰めない。

`max_overcooling` の既定値は2 K（有限の非負値。10 K の上限は撤廃）。温度が下限より低いとき、湿度優先は
除湿のための加熱を行わず、湿度未達を残す。`min_coil_temperature` の既定値は5℃（0～20℃）。
温湿度満足は理想再熱設備を仮定する。`reheat_cop=1` は電気ヒーター相当で、
再熱電力を冷却機の消費電力に加える。再熱能力は無制限とする。
温湿度満足では、冷房期間でも室温が設定より低ければ理想再熱で補い、乾燥時は加湿しない。
機器の `Q.cooling` 能力上限は、再熱前の冷却コイルの顕熱＋潜熱に適用する。
`model=IDEAL` は従来どおり冷却COPを持たないため、機器電力量の比較にはCOPモデルを指定する。明示した再熱の電力はIDEALでも別途計上する。

DUCT_CENTRALの湿度制御では、顕熱・除湿・再熱要求と過冷却制約を共通の運転要求として扱う。
顕熱がゼロでも除湿要求があれば起動し、温湿度の要求がなくなれば停止する。数値反復中の
送風保持は、時間ステップをまたぐ発停ヒステリシスとは区別する。

風量は、現在の運転点と顕熱・潜熱要求から求めた候補を比較する。両者とも温湿度を満たせない
場合は、制御用最低風量から最大風量までの5候補（区間の両端と4等分点）に探索を広げる。
同じ候補は再評価せず、選んだ候補を戻した場合は再度収支を検査する。各候補で換気、熱、湿気、
コイル・能力・過冷却制限を解き直し、時間段階の開始時の蓄積量を共通に使う。
各時刻は通常の最大風量で初期状態を求める。前時刻の過冷却時の低風量と、更新された設定温度を
そのまま組み合わせない。探索中に温度が計算範囲を外れた候補や連成反復上限に達した候補は、
理由を記録し、直前に収支が成立した状態へ戻して除外する。除外は物理的に不可能という判定ではなく、
その候補の解を確認できなかったという意味である。初期状態や選定候補の失敗、圧力・湿気・熱の
個別ソルバの未収束はエラーのまま扱う。除外した候補の値は出力や蓄積量に使用しない。
要求温度以下（許容0.1 K）の候補では湿度未達を先に減らし、RHの上限も満たす候補
（許容0.1 percentage points）では電力を比較する。室温の上昇だけでRHが下がった候補を
有利に扱わない。有限候補間の選択であり、連続的な大域最適化やRH達成の保証ではない。

制御用最低風量比は既存の `min_process / Q.rtd` による。これは実機の最低風量を
測定した値ではなく、温度優先と共通の制御下限である。PQファンは基準曲線の流量を
速度比倍、圧力を速度比の二乗倍にし、実風量は回路網で解く。固定流量循環では設計風量に
比率を掛ける。ACの熱・水分・COP計算には、いずれも最終的な実風量を渡す。
複数台は一台ずつ風量候補を進め、各候補で全台の温湿度・能力の連成を解く。
吹出RH≦100％、水分収支、全熱能力の最終受理判定は従来と共通である。
飽和防止にはfloat32丸めの安全余裕を持つ目標湿度を使い、受理時はAC・吹出プレナムの
実際の状態とfloat32出力をそれぞれRH100％以下で検査する。安全余裕の目標が微小に動いても、
実状態が非飽和で湿度境界の欠損が許容内なら再反復せず、解いた水分量も書き換えない。
乾きコイルへ切り替わった際は、旧吹出湿度の固定境界を解除して混合として解く。
選定された風量比・実風量・発停・室温湿度・電力・目標達成の有無を `solver.log` に記録する。

## 出力と成功判定

| artifact | 内容 |
|---|---|
| `aircon_reheat` | 再熱量 [W]。既存の冷却顕熱・潜熱には含めない。 |
| `aircon_room_rh` | 設定対象室の実際の相対湿度 [%] |
| `aircon_humidity_unmet` | 冷房時のRH上限超過 [percentage points]。停止・暖房時は0。 |
| `aircon_temperature_unmet` | 冷房: max(0, 室温−設定)、暖房: max(0, 設定−室温) [K]。AUTOは絶対差、停止時は0。過冷却は冷房未達に含めない。 |

`status=ok` は数値解と物理制約が成立したことを表す。温湿度設定の達成とは区別する。
能力、過冷却下限、コイル条件、送風・接続条件のために目標が達成できない場合は、
未達量をそのまま記録する。年間の未達時間は、用途に応じた温度・湿度の許容帯を決めて集計する。

検証は `engine/tests_py/test_room_humidity_control.py`、PQファンの起動・停止・再起動は
`engine/tests_py/test_humidistat_fan_network.py`。従来条件の回帰検証も併用する。

## 旧「理想60％」条件の移行

2026-11-14の修正で、温度優先の `pre_rh` による独立した吹出湿度の指定を廃止した。
旧方式は、冷却が小さくても室設定温度・RHから換算した水分量まで除湿でき、再熱なしの
冷却過程として整合しなかった。温度優先では `pre_rh` の有無・値で処理量や電力は変わらず、
室RH未達の評価だけが変わる。`latent_method="none"` は吹出の飽和防止に必要な凝縮のみ行う。
湿度60％を制御目標にする比較には `humidity_priority` または `temperature_humidity` を明示する。
旧「理想60％」の年間結果・電力量は修正後の結果ではないため、比較には再計算が必要である。
なお、DUCT_CENTRALの電力モデルには従来から顕熱と潜熱の両方を渡している。
本修正は電力を後付けする処理ではなく、その入力となる冷却・除湿過程の修正である。


## 複数台の湿度制御

異なる設定対象室が湿気でつながる場合、各空調の吹出境界から各設定室への応答行列を作り、要求吹出湿度を同時に求める。基準解1回と台数分の右辺計算で行列分解を共有し、次の反復にも分解を再利用する。コイル温度・能力・過冷却幅の制約に当たった機器は、他機器の計算では実際の吹出境界に固定する。

同じ設定対象室を複数台が直接制御する構成は、熱側の拘束が重複するため入力エラーになる。設定対象室を分けるか、一台の集約機器としてモデル化する。

`temperature_humidity` の目標絶対湿度は要求設定温度で換算する。能力不足で室温が設定からずれると相対湿度もずれるため、温度未達と湿度未達を併せて評価する。湿度のために温度設定を変更する場合は `humidity_priority` を使用する。
